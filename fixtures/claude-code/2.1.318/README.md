## Findings: S22

- **The hooks of a background session see another terminal than the driver's.** All six hooks had exactly `WARP_FOCUS_URL` and `WARP_TERMINAL_SESSION_UUID` with the IDs of **another** Warp tab (`1b10f293…`) than the driver's (`16e5a860…`). `TERM_PROGRAM`, `TERM_PROGRAM_VERSION` and `__CFBundleIdentifier` were not set, nor any other allowlisted variable. The driver's shell had all five Warp variables (action `driver terminal`). That these are the daemon's values follows from the process chain below; checked by hand on 2026-11-04 after the run, outside this fixture, with `ps -E` (variable names and the first eight hex digits only): the daemon 39632 had both Warp IDs `1b10f293…` plus `TERM_PROGRAM`, `TERM_PROGRAM_VERSION` and `__CFBundleIdentifier` and no other allowlisted variable, the fresh pty host 63991 and spare 63994 had both Warp IDs `1b10f293…` and none of the other three. The claimed spare 39661 was gone by then.
- **The daemon existed before the run.** `claude daemon run` (pid 39632, ppid 1) had been started at 01:11:12 local time, about seven and a half hours before the run (action `daemon processes before`), so not by the driver; what started it is not recorded. Its spare `claude bg-spare` (39661, under `claude bg-pty-host` 39658, both started at 01:11:15, three seconds after the daemon) was in that list too. `claude --bg` handed the job to that spare (the claimed status file's `pid` and the `claude agents` entry are 39661). A fresh pty host and spare (`claude bg-pty-host` 63991 under the daemon, `claude bg-spare` 63994 under it) were not in the list taken at 08:44:17.106 and have the start time 08:44:17 (`ps` shows whole seconds), so they started while `claude --bg` was running (it returned at 08:44:18.082) and before the claimed file's `startedAt` (08:44:18.467); all times local, from `timeline.jsonl`. After `claude stop` and `claude rm` the claimed spare was gone; the fresh spare stays, as before the run.
- **Process chain** of every hook (`log.sh`): `claude bg-spare` 39661 → `claude bg-pty-host` 39658 → `claude` (`daemon run`) 39632 → `launchd`. The hooks' `$PPID` and the status file's `pid` are the spare.
- **`CLAUDE_CODE_SESSION_KIND` and `CLAUDE_BG_BACKEND` are not in the hooks' environment.** `log.sh` recorded neither for any hook. The spare processes themselves have them (`CLAUDE_CODE_SESSION_KIND=bg`, `CLAUDE_BG_BACKEND=daemon`, read by hand with `ps -E` from the spare 39661 before the run and from the fresh spare 63994 after it; not part of this fixture), but not in the hooks' environment. `ps -E` shows the environment a process was started with, so how they go missing on the way to a hook is not observed. The hooks' `CLAUDE_*` names differ from S21's only by `CLAUDE_JOB_DIR` and `CLAUDE_CODE_HOST_SHORT_TEMP_DIRS` (names only; values not recorded).
- **Nothing in the payloads marks a background session.** Every payload has the same keys as the interactive S21 session's in the same version. `SessionEnd` after `claude stop` has `reason: "other"` (011).
- **The status file has `"kind": "bg"`** in every snapshot (001–010), so the mapping yields `process_kind: "bg"`, and since revision 3 of `model/claude-code-session.json` `job_id: "35ad01b4"` from `jobId` (`status-expected/`). Also: `entrypoint: "cli"`, no `spare` key; `jobId` is the id `claude --bg` printed and `claude stop`/`rm` take (`claude attach` too, S24). `procStart` is when the spare process started (`Wed Nov  4 00:11:15 2026`, UTC), `startedAt` when it claimed the job. `name` starts as the prompt and is replaced by an automatic name (`nameSource: "auto"`, 010). The capture starts with the claim: `watch-sessions.py` records only files whose `cwd` lies in the capture directory, so whether the spare 39661 had a file of its own before the claim is not recorded. The claimed file was deleted on `claude stop`, before `SessionEnd`. Checked by hand on 2026-11-04 after the run, outside this fixture: the fresh unclaimed spare 63994 had no `63994.json` (and no key file) in `~/.claude/sessions/`, and `CLAUDE_CONFIG_DIR` was not in its `ps -E` environment.
- `claude agents --json` lists the session with `"kind": "background"`, not `bg`.
- The background session's project hooks ran from the capture directory's `.claude/settings.json` (its cwd). It needed no input: the driver typed nothing into it and it reached `Stop`, and the output of `claude logs` after the `Stop` (in the raw capture `tty/S22.log`, not in the repository) shows the banner, the prompt, the hooks' progress lines and the answer, and no dialog.

## Findings: S24

The question (#30): while a background session is attached, the `claude attach` client runs in a real terminal tab. Can an app learn that tab from anything Claude Code writes, or only from the attach process's environment?

- **No file name, socket folder entry or status key names the attach client's tab, and the hooks don't see it.** All eight hooks, before the attach and during the turn typed through the attach client (012, 013), had exactly `WARP_FOCUS_URL` and `WARP_TERMINAL_SESSION_UUID` of the daemon's Warp tab (`1b10f293…`, as in S22; `terminal.json`), not the driver's (`16e5a860…`, action `driver terminal`). Their process chain (`log.sh` `.meta` files of the raw capture, not in the fixture) stayed `claude bg-spare` 10788 → `claude bg-pty-host` 10785 → `claude` (`daemon run`) 39632 → `launchd`. Attaching changes nothing in the hooks' environment, and the payloads of the attached turn have the same keys as the first turn's: nothing in them marks that it was typed through an attach client.
- **The attach client's environment has the tab.** The client (pid 63430, `ps` command line `claude attach a7741313`) ran on the driver's pseudo-terminal (`ttys043`, state `Ss+`) with no child processes, as a child of the driver. `ps -E` showed the driver's five Warp variables (`TERM_PROGRAM`, `TERM_PROGRAM_VERSION`, `__CFBundleIdentifier`, `WARP_FOCUS_URL` and `WARP_TERMINAL_SESSION_UUID`, `16e5a860…`) and no other allowlisted variable (`attach_client.terminal` in `observe attached` and `observe attached after the turn`). Per `claude attach --help`, not tested: `claude attach` also takes part of a session name, so a client's command line can carry a name instead of the job id.
- **The attach journal names the client's pid, nothing else does.** `~/.claude/daemon/attach-journal/` got one new file while attached, `df7c386c-0922-4bb6-825f-4f42f95185d6.json`, gone after the detach (`attach_journal_new` in `observe attached` and `observe attached after the turn`, absent in `observe after detach`). Its content: `gestureId` (the file name), `surface: "bg_cli"`, `startedAtEpochMs` (261 ms after the driver started the client), `attempt: 1`, `pid: 63430` (the attach client), `procStart` (the client's start, UTC), `marksExpected: false`, `daemonBooted: false`, `attachCold: false`, `via: "spare"`. It names neither the job nor the session, and no terminal identifier. Three files from before the run stayed in the folder throughout (names only in the fixture; checked by hand, outside this fixture: they have `surface: "fleet"` and a `startedAtEpochMs` on 2026-11-02 or 2026-11-05).
- **Unchanged by the attach, in all four `observe …` actions:** the names in `~/.claude/sessions/` (no status file for the client, no new file at all), `/tmp/cc-socks/` (no socket for the client; `10788.sock` is the session's `messagingSocketPath`) and the daemon's socket folder (the job's `rv/a7741313.sock` was there before the attach); the job folder `~/.claude/jobs/a7741313/` (`state.json`, `timeline.jsonl`, `tmp`), the key paths of its `state.json` and its `state` (`done`) and `backend` (`daemon`); the key paths of the job's `roster.json` entry and its `pid` (10785, the pty host) and `replPid` (10788); the job's entry in `claude agents --json` (`pid` 10788, `kind: "background"`, `status: "idle"`, `state: "done"`), which names no client or tty; the daemon processes. The job's status file changed only for the attached turn (011 `busy`, 014 `idle`), with the same keys as before: no attach marker.
- **The client's open files** (`lsof`): the capture directory as cwd, the Claude Code binary and four system database files under `/private/var/db/` (`txt`), the tty on fds 0, 1, 2, 4, 6 and 11, two unix sockets without a path (`->0x…`, so which daemon socket they connect to is not visible), and one IPv4 connection (address not recorded).
- **`claude attach` takes the status file's `jobId`.** The job's only status file `sessions/10788.json` had `jobId: "a7741313"`, the id `claude --bg` printed (action `status file job id`). The driver passed that value to `claude attach`; the client drew the session ("Attaching…", then its conversation, in the raw `tty/S24.log`, not in the repository), and the prompt typed into it reached the session (012, 013, with the job's `session_id`). Every golden status file has `job_id: "a7741313"` (`status-expected/001` to `014`).
- **Detach:** Ctrl+Z ended the client: it exited with status 0 about 0.6 s later (action `attach client exited`). The session kept running: no hook event and no change of its status file followed until `claude stop`, which deleted `10788.json` before `SessionEnd` (`reason: "other"`, 015), as in S22.
- **No short-lived `claude bg-spare` status file during this attach.** `watch-sessions.py` recorded no `untracked` file (a status file that appears and is neither in the capture directory nor of the job's session) and no file of the job's session other than `10788.json`, and the `sessions` names are the same in all four `observe …` actions. The fresh spare (`claude bg-pty-host` 62864, `claude bg-spare` 62868, started during `claude --bg`, not in `daemon processes before`) had no status file in any of them. So the file of about 1.5 s seen during an earlier attach (contract §13) did not recur here; what made it appear then is not known.
- **Daemon processes:** the job went to the spare 10788 (pty host 10785), which the daemon had started at 09:34:05 local time, about an hour and a half before the run (status file `procStart` `Thu Nov  5 08:34:05 2026`, UTC). The capture starts with the claim, and the watcher does not record files that exist when it starts; checked by hand a few minutes before the run, outside this fixture: there was no `10788.json` in `~/.claude/sessions/`. The attach started no process in the daemon. After `claude stop` and `claude rm` the spare 10788 and its pty host were gone; the fresh spare stays. `sessions/` held `63994.json`, `7299.json` and `8000.json` in every list: the files of the spare 63994 (S22's fresh spare) and of the spares 7299 and 8000 under the 2.1.316 pty hosts. Checked by hand after the run, outside this fixture (`ps` and the keys `kind`, `spare`, `status`, `jobId` and `startedAt` only): each process still ran with its listed start time, and each file had `kind: "bg"`, a `jobId`, no `spare` key and a `startedAt` after its process's start (63994: 2026-11-05 09:34:00 local, after S22's check on 2026-11-04 and five seconds before the daemon started the spare 10788; 7299 and 8000: three and six seconds after their start on 2026-11-02). So these are spares claimed by the user's own jobs between the runs, not unclaimed spares with a status file (contract §13). Their names are kept unmasked because their pids appear in the run's process lists.
- The driver ran under a Claude Code session in the Warp tab (the attach client's chain upward: `claude` 63430 → the driver (`Python`) → `zsh` → `claude` → `-zsh` → Warp (`stable`) → `launchd`); the background session was started with the driver's environment minus Claude Code's own variables (`clean_env()`), as in S22.
